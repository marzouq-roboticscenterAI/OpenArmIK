## Important

1. **`oa_can_probe_expected` can declare stale and already-enabled motors successfully probed.** The API sends refreshes and then accepts every queued matching frame, but frames carry no receive timestamp/epoch and the transport has no deadline/timestamp contract ([`can/include/openarm_can.h:85`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/include/openarm_can.h:165`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/src/openarm_can.c:301`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:310`](../../OpenArmIK-wt-can/can/src/openarm_can.c)). Any pre-request frame sets `fresh_mask`; a continuously busy/unexpected stream can also prevent termination indefinitely. Worse, status 1 (enabled) is treated as healthy and marked fresh ([`can/src/openarm_can.c:220`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:327`](../../OpenArmIK-wt-can/can/src/openarm_can.c)). The success test explicitly pre-enqueues enabled feedback before the refresh sends, thereby enshrining both defects ([`can/tests/test_openarm_can.c:244`](../../OpenArmIK-wt-can/can/tests/test_openarm_can.c), [`can/tests/test_openarm_can.c:252`](../../OpenArmIK-wt-can/can/tests/test_openarm_can.c)). This contradicts the stated torque-disabled/fresh expected-node probe and can falsely pass a dead or armed node.

2. **The manifest is not verified against hardware.** It stores motor family and `serial`, but validation only checks local syntax and the probe emits only refresh frames ([`can/include/openarm_can.h:133`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/src/openarm_can.c:259`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:301`](../../OpenArmIK-wt-can/can/src/openarm_can.c)). There is a register-query encoder but no register-response decoder, and the probe never queries motor type, serial, firmware/configuration, timeout, control mode, P/V/T limits, direction, or gear. A different motor at the expected ID passes and is decoded using the manifest's claimed range, yielding plausible but wrong physical values. Thus the README's “verification contract” is materially weaker than the commissioned-manifest gate in the research/design reports.

3. **The Linux enumerator's request path is invalid for an unconnected netlink socket.** It creates `AF_NETLINK` and immediately calls `send()` without `connect()` or a destination-bearing `sendto`/`sendmsg` ([`can/src/openarm_can_linux.c:57`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c), [`can/src/openarm_can_linux.c:65`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c)). `send()` on a connectionless socket with no peer fails with `EDESTADDRREQ`; Linux's `netlink(7)` example supplies a kernel `sockaddr_nl` to `sendmsg`. The function therefore returns `OA_CAN_EIO` before listing anything on the ordinary path. The suite intentionally never invokes it ([`can/README.md:28`](../../OpenArmIK-wt-can/can/README.md)). This conclusion is static; no netlink/CAN query was run.

4. **The advertised versioned C ABI is not stable or size-safe.** Public function signatures and records use implementation-defined C enums ([`can/include/openarm_can.h:25`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/include/openarm_can.h:39`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/include/openarm_can.h:93`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/include/openarm_can.h:133`](../../OpenArmIK-wt-can/can/include/openarm_can.h)). On this compiler, a probe printed default `enum/status/command/manifest = 4/4/56/128` bytes but `-fshort-enums` produced `1/1/56/120`; a library/client flag mismatch changes both calling convention risk and record layout. In addition, output functions ignore caller-supplied `struct_size`/`abi_version` and unconditionally `memset`/write the full current struct ([`can/src/openarm_can.c:78`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:164`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:209`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:298`](../../OpenArmIK-wt-can/can/src/openarm_can.c)). A safe probe with `oa_can_limits.struct_size = 8` returned success and overwrote it as an 88-byte record. The metadata therefore cannot protect an older/smaller caller from overwrite and does not deliver the compatibility its documentation implies.

5. **The rtnetlink parser contains alignment UB and lacks basic message-bound checks.** `char buffer[8192]` is cast to the more-aligned `struct nlmsghdr *` ([`can/src/openarm_can_linux.c:51`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c), [`can/src/openarm_can_linux.c:78`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c)); GCC 15 rejects this under `-Wcast-align=strict -Werror`. Unlike the aligned buffer in the `netlink(7)` example, C does not guarantee this stack byte array's alignment. The code also dereferences `ifinfomsg` without first checking that `nlmsg_len` contains it, uses unbounded `strcmp` on an attribute without establishing NUL termination, does not reject/trap truncation or validate sender/sequence, and loops forever on `recv()==0` ([`can/src/openarm_can_linux.c:31`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c), [`can/src/openarm_can_linux.c:36`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c), [`can/src/openarm_can_linux.c:69`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c), [`can/src/openarm_can_linux.c:94`](../../OpenArmIK-wt-can/can/src/openarm_can_linux.c)). This needs parser-level synthetic tests, not a live-interface test.

## Minor

1. **“Diagnostics-only” is a policy claim, not an API boundary.** The public API constructs MIT and enable frames and exposes a generic transport `send` callback ([`can/README.md:3`](../../OpenArmIK-wt-can/can/README.md), [`can/include/openarm_can.h:165`](../../OpenArmIK-wt-can/can/include/openarm_can.h), [`can/include/openarm_can.h:188`](../../OpenArmIK-wt-can/can/include/openarm_can.h)). A caller with a physical transport can send those frames directly. Keeping physical transport absent is useful, but the library cannot claim to enforce an incapable-of-control boundary; codec/control frame types should be separated or the documentation narrowed.

2. **The fake transport does not validate the safety property its tests name.** `oa_fake_send` accepts arbitrary valid frames, including enable/MIT, while `oa_can_fake_torque_enabled` always reports false and the `FAULT` lifecycle is never entered ([`can/src/openarm_can.c:345`](../../OpenArmIK-wt-can/can/src/openarm_can.c), [`can/src/openarm_can.c:412`](../../OpenArmIK-wt-can/can/src/openarm_can.c)). Consequently the “lifecycle” test only proves a constant accessor, not rejection/tracking of control frames.

3. **The explicit MSVC branch is not build-portable as written.** Tests unconditionally link Unix `m` even under MSVC ([`can/CMakeLists.txt:13`](../../OpenArmIK-wt-can/can/CMakeLists.txt), [`can/CMakeLists.txt:26`](../../OpenArmIK-wt-can/can/CMakeLists.txt)). No non-Linux/MSVC build test accompanies the claimed standalone C11 surface.
