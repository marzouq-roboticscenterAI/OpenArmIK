# OpenArm 1.0 independent evidence audit

Checked 2026-07-28 against current upstream `main`: central site repo `990fda9`, description `6c7b720`, CAN `c32ecd3`, ROS 2 `4e837e1`, hardware `12c0751`. No hardware commands were sent.

## Identity and authoritative assets

- Canonical name is **OpenArm**, an Enactic, Inc. project (originally associated with its Tokyo HI Lab), not the unrelated “Open Arms” projects and not an arbitrary site using the OpenARM spelling. The current project home is [openarm.dev](https://openarm.dev/) and its own repository index is [github.com/enactic/openarm](https://github.com/enactic/openarm). Those two sources cross-link and identify Enactic; they link `docs.openarm.dev` and contact `openarm@enactic.ai`. `openarm.io` is not linked by the canonical repository and should not be used as an authority.
- Canonical v1 hardware/manufacturing source: [enactic/openarm_hardware](https://github.com/enactic/openarm_hardware). Contrary to the central index's broad “complete CAD data” description, the current repo README points v1 CAD/STEP/STL/wiring to this [Google Drive folder](https://drive.google.com/drive/folders/1a9ec9vzBV_D-AX9s_LOkBVy3ZXDC1kJT?usp=sharing); the large CAD assets are not actually versioned in the Git tree.
- Canonical models: [enactic/openarm_description](https://github.com/enactic/openarm_description), especially the pinned [v1.0 xacro tree](https://github.com/enactic/openarm_description/tree/6c7b720f1ba48e8bafa3a3dc752c45f397b42221/assets/robot/openarm_v1.0). Canonical motor transport: [enactic/openarm_can](https://github.com/enactic/openarm_can). Canonical ROS 2 integration: [enactic/openarm_ros2](https://github.com/enactic/openarm_ros2). The archived, version-selected [1.0 documentation](https://docs.openarm.dev/1.0/) is authoritative for the old hardware, but several commands/paths in it are stale relative to current repositories.

## What “7 DOF” and the variants actually mean

- One arm has **7 revolute arm joints**, J1–J7, and the follower gripper has a separate rotary **J8 motor**. It is therefore 7 arm DOF, 8 motors per follower arm—not an 8-DOF serial arm. Motor assignment in the current ROS hardware source is J1–J2 DM8009, J3–J4 DM4340, J5–J7 DM4310, J8 DM4310 ([header](https://github.com/enactic/openarm_ros2/blob/4e837e1d0dae692ff67b560b69d8d281d7a8d4ed/openarm_hardware/include/openarm_hardware/openarm_simple_hardware.hpp)).
- Physical left and right arms are mirrored at J6/J7 and use side-specific parts; the assembly guide explicitly calls out those differences ([J5–J7 guide](https://docs.openarm.dev/1.0/hardware/assembly-guide/j5-j6-j7-sub-assembly/)). “Leader” and “follower” arms are otherwise physically identical; their end-effectors differ ([power/CAN guide](https://docs.openarm.dev/1.0/hardware/wiring-and-casing-guide/power-can/)). A follower has the driven parallel gripper; a v1 leader uses a different hand/pincer assembly but still contains J8. These are not different 7-joint kinematic chains.
- Current v1 xacro defaults to a **bimanual** body with `openarm_left_*` and `openarm_right_*`. It still contains `bimanual:=false`, but that emits a generic `openarm_*` chain whose mirror selection falls through to the left-style reflection; there is no current v1 right-only/left-only preset. Do not infer v2's explicit single-arm presets apply to v1. See [entry xacro](https://github.com/enactic/openarm_description/blob/6c7b720f1ba48e8bafa3a3dc752c45f397b42221/assets/robot/openarm_v1.0/urdf/openarm_v10.urdf.xacro) and [arm macro](https://github.com/enactic/openarm_description/blob/6c7b720f1ba48e8bafa3a3dc752c45f397b42221/assets/robot/openarm_v1.0/urdf/arm/openarm_arm.xacro).

The bimanual joint names are `openarm_left_joint1`…`joint7` and `openarm_right_joint1`…`joint7`; links are correspondingly `openarm_{left|right}_link0`…`link7`. Axes below are expressed in each joint's URDF joint frame. Origins are parent-to-child joint origins in metres/radians.

| J2 | `-.0301 0 .06` | left `-pi/2 0 0`, right `+pi/2 0 0` | `-1 0 0` | `-1 0 0` | `[-3.316125, .174533]` | `[-.174533, 3.316125]` |

Treat those shifts as part of the canonical coordinate convention, not alternate physical stops.

## End effector and model-accuracy limits

- Wrist/output link is `openarm_{side}_link7`. The parallel gripper adds a fixed `openarm_{side}_hand` at `0 0 .1025`, then a fixed `openarm_{side}_hand_tcp` at `0 0 .0835` from `hand`; TCP is therefore nominally 0.186 m along link7 +Z. There is **no canonical `claw`, `tool0`, or `ee_link` frame**. Source: [gripper xacro](https://github.com/enactic/openarm_description/blob/6c7b720f1ba48e8bafa3a3dc752c45f397b42221/assets/robot/openarm_v1.0/urdf/ee/parallel_link/openarm_parallel_gripper.xacro) and [kinematics](https://github.com/enactic/openarm_description/blob/6c7b720f1ba48e8bafa3a3dc752c45f397b42221/assets/end_effector/parallel_link/config/kinematics.yaml).
- The physical J8 is rotary (60 degrees closed-to-open; closed is motor zero), but URDF replaces it with one actuated prismatic `finger_joint1` (0–0.044 m, axis outward) and mimicked `finger_joint2`; jaw separation is 88 mm ([gripper specification](https://docs.openarm.dev/1.0/hardware/specifications/gripper/)). This is a planning abstraction, not the exact actuator linkage.
- The ROS bridge itself labels gripper motor↔prismatic conversion “approximate” and “true mappings unimplemented” ([source](https://github.com/enactic/openarm_ros2/blob/4e837e1d0dae692ff67b560b69d8d281d7a8d4ed/openarm_hardware/src/openarm_simple_hardware.cpp)). MoveIt declares `hand` as the semantic end-effector parent, not the newer `hand_tcp` ([SRDF](https://github.com/enactic/openarm_ros2/blob/4e837e1d0dae692ff67b560b69d8d281d7a8d4ed/openarm_bimanual_moveit_config/config/openarm_v1.0/openarm_bimanual.srdf)). An IK application must explicitly choose `link7`, `hand`, or `hand_tcp` and must not assume MoveIt's choice equals fingertip centre.
- The meshes/nominal transforms are official CAD-derived assets, but upstream publishes no tolerance, calibration-error, repeatability, or URDF validation result; its [v1 FAQ](https://docs.openarm.dev/1.0/faq/) says accuracy/repeatability documentation is still being prepared. The model is the canonical nominal model, not evidence of millimetre-accurate FK on an assembled unit.
- Version drift is real: archived v1 docs cite now-absent paths such as `urdf/robot/v10.urdf.xacro`, advertise `ee_type:=none`, and describe single-arm support. Current source moved to `assets/robot/openarm_v1.0/...`, hard-codes the v1 parallel-link EE in the entry point, and defaults bimanual. Pin a description commit; do not copy old paths blindly.

## ROS/RViz/dual-arm claims

- Upstream **does** supply ROS 2, RViz, ros2_control, fake hardware, bimanual launch, and a bimanual MoveIt configuration. Evidence: [description/RViz guide](https://docs.openarm.dev/api-reference/description/), [ROS 2 repo](https://github.com/enactic/openarm_ros2), [bimanual launch](https://github.com/enactic/openarm_ros2/blob/4e837e1d0dae692ff67b560b69d8d281d7a8d4ed/openarm_bringup/launch/openarm.bimanual.launch.py), and [v1 MoveIt config](https://github.com/enactic/openarm_ros2/tree/4e837e1d0dae692ff67b560b69d8d281d7a8d4ed/openarm_bimanual_moveit_config/config/openarm_v1.0).
- That does **not** mean mature/safety-certified hardware support. The v1 docs call the hardware bridge unstable, especially the gripper, and MoveIt “actively being developed” ([v1 control guide](https://docs.openarm.dev/1.0/software/ros2/control/)). Current hardware code still hard-codes motor ordering, exposes position/velocity/effort simultaneously with a TODO about undefined behaviour, and uses approximate gripper mapping. RViz visualization is the strongest-supported claim; hardware execution deserves independent bench validation.

## CAN, IDs, calibration, firmware, and safety

- Each arm normally has its own bus. Motor sender/master pairs repeat per bus: J1 `01/11`, J2 `02/12`, … J7 `07/17`, J8 `08/18` ([ID guide](https://docs.openarm.dev/1.0/software/setup/motor-id/)). The four-arm leader/follower convention is interface `can0` right leader, `can1` left leader, `can2` right follower, `can3` left follower; the guide confusingly calls these adapter “CAN IDs.” A two-arm follower/robot model instead defaults right `can0`, left `can1`.
- Host control is Linux SocketCAN using a CAN-FD-capable USB adapter. The v1 BOM specifies **two Pibiger USB2CANFD converters** for a bimanual pair, and the official FAQ warns that other devices may behave unexpectedly ([BOM](https://docs.openarm.dev/1.0/hardware/bill-of-materials/electrical/), [FAQ](https://docs.openarm.dev/faq/)). Initial ID/parameter work uses the DaMiao USB debugger on Windows over **UART 921600 bps**, not CAN.
- Protocol is DaMiao motor framing. Current `openarm_can` implements MIT, position+velocity, velocity, and position+force modes ([library](https://docs.openarm.dev/1.0/software/can/)). Classic CAN is 1 Mbit/s. Recommended/default CAN-FD is 1 Mbit/s arbitration plus 5 Mbit/s data; motor and SocketCAN rates must match ([v1 CAN setup](https://docs.openarm.dev/1.0/software/setup/can-setup/)). CAN-FD is the current xacro/ROS hardware default, not proof that an arbitrary adapter or an as-shipped motor is already configured for 5 Mbit/s.
- Required setup order is IDs → matching CAN interface → communication test → motor baud/zero calibration → verify IDs/rate → only then demo/ROS. Motor parameter flash is rated for only 10,000 writes per the [configuration guide](https://docs.openarm.dev/1.0/software/setup/motor-config/).
- “Homing” is not sensor-based. No home switch is documented. Current calibration deliberately drives each joint/gripper into mechanical stops using velocity/torque thresholds, moves to inferred nominal offsets, disables, then writes zero ([script](https://github.com/enactic/openarm_can/blob/c32ecd31da267967f0c913c2118c843177d88b91/setup/openarm-can-zero-position-calibration)). It moves automatically and must be run one arm at a time with an E-stop and clear workspace. The script still contains a `TODO` for precise-home refinement, so do not treat it as metrology-grade calibration.
- Low-level CAN is **not a safety layer**. MIT packing clamps only to broad motor protocol bounds (e.g. ±12.5 rad), not the URDF mechanical ranges; other float command modes do not enforce URDF joint limits. No automatic host feedback watchdog or E-stop integration is evident in the high-level library. The ROS hardware plugin enables all motors on activation and immediately runs a two-second return-to-zero interpolation. Upstream's [safety guide](https://docs.openarm.dev/1.0/getting-started/safety-guide/) requires physical exclusion, PPE, secure mounting, E-stop/power-disconnect readiness, and warns that loss of power drops a held load. Software “disable” is not the physical E-stop.
- Firmware update is **not a normal v1 prerequisite**: the archived v1 setup has no firmware step. Current upstream calls updating optional, only for problems or when instructed, and its files are explicitly for hardware V3; wrong hardware/model firmware can damage the motor ([current firmware guide/source](https://github.com/enactic/openarm/blob/990fda921c82ae9d12b00f23e449793a9a313afd/website/docs/setup/openarm-setup/6-motor-firmware-update.mdx)). Verify motor hardware/software version with the DaMiao tool before any flash.

## Explicit unknowns / decisions that must be measured or confirmed

1. Exact assembled unit revision, motor hardware/firmware versions, motor baud settings, zero offsets, side, and whether it is leader or follower.
2. Actual base-to-world transform and desired IK tip (`link7`, `hand`, or `hand_tcp`); no generic “claw frame” exists.
3. Unit-specific link/fixture deflection, backlash, joint-zero error, TCP calibration, accuracy, and repeatability. Upstream gives no validated error budget.
4. Whether the installed USB-CAN adapter reliably supports the required FD timing/termination. Confirm 120-ohm termination and wiring; do not assume CANable compatibility.
5. Whether current ROS hardware behaviour is acceptable for this application; upstream code and docs still disclose unfinished gripper mapping and active development.
